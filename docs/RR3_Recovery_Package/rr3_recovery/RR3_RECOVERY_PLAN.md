# RR3 Android ARM64 → Switch：停滞排查与恢复计划

版本：2026-09-15 / v1.0  
目标读者：项目负责人、在本地仓库执行任务的 Codex。  
输入：用户提供的 `PROJECT_STATUS.md`，文档更新时间为 2026-09-09。

> 当前只审阅了状态报告，没有取得项目源文件、原始 DSO、APK、反编译正文或真机日志。下文严格区分“报告记载”“本次静态计算确认”“待验证假设”和“建议实现”。这不是已经修复或真机验证过的补丁。

## 0. 决策摘要

**保留已取得的运行基础，不推倒重写。停止把未初始化的业务对象替换成全 stub vtable；先统一地址与指针层级，再恢复真实对象的初始化与事件链。**

把当前问题暂时命名为 **`POST_SPLASH_INIT_STALL`（开屏之后初始化状态停滞）**，不要直接把它当作已经证实的 CPU 死循环。

报告记录帧循环在 `connect()` 快速失败后可继续到 frame 170+，但没有菜单资产加载。这个组合更支持“主循环仍在运行，某个前置状态/异步任务未完成”；仍需真实线程与事件日志排除其他线程的忙等、死锁或任务饥饿。[P：§2]

本轮只追求一个结果：

**通过真实初始化路径，定位并推动第一个未完成环节，最终看到真实菜单请求被消费并触发资产读取。**

不要把“不崩溃”“hideSplash 被调用”“进入了某个函数”或“帧数增加”单独视为菜单恢复成功。

保留原目标与约束：[P：§1]

- 最终仍为原生 libnx NRO：启动 → 菜单 → 离线比赛 → Joy-Con 驾驶 → 完赛 → 安全退出。
- 不绕过 DRM、不伪造账户或授权、不公开分发 EA 数据；只做离线单人。
- 七个 ROMFS 数据卷不变；部署仍以替换 NRO 为主，不重新复制或打包近 9 GB 资源。
- 最小化真机往返次数；当前不扩展画质、超频、多车比赛或通用 Android 兼容层。

## 1. 本次已经确认与尚未确认的内容

### 1.1 确认：地址表有一处算术错误

以报告里的 `onViewRenderJNI ELF VA = 0x12B3614` 为基准，复算结果如下。这只验证表内算术，**不等于验证这些 VA 在二进制里对应的真实函数或变量**。

| 报告标签 | 报告 ELF VA | 报告 delta | 复算 delta | 结论 |
|---|---:|---:|---:|---|
| onViewRenderJNI | `0x12B3614` | `0` | `0` | 基准 |
| cloudcell GOT | `0x1F6D5D0` | `+0xCB9FBC` | `+0xCB9FBC` | 算术一致 |
| 菜单加载器全局 | `0x1F6DF50` | `+0xCBA93C` | `+0xCBA93C` | 算术一致，指针性质待查 |
| FUN_014bcbac | `0x13BCBAC` | `+0x109598` | `+0x109598` | 算术一致，命名空间待查 |
| FUN_012034fc | `0x11034FC` | `-0x1B0118` | `-0x1B0118` | 算术一致，命名空间待查 |
| CloudcellResume | `0x1CF2AD8` | `+0xA3F4C4` | `+0xA3F4C4` | 算术一致 |
| hideSplash 检查 | `0x12AEEE0` | `-0x4E1634` | **`-0x4734`** | **不一致** |

计算：

```text
0x12AEEE0 - 0x12B3614 = -0x4734
0x12B3614 - 0x4E1634 = 0xDD1FE0
```

来源：[P：§3，地址映射]；复算见附件 `RR3_STATUS_AUDIT.json`。

执行要求：在代码、地址配置、补丁表中搜索这两个 delta 及其计算来源。若错误仅存在于报告，更新文档，不改代码；若运行代码使用了错误 delta，必须先根据原始 DSO 与指令匹配确认实际目标，再修复。**不能仅凭此表把一次文档修订变成盲目改写内存。**

另外，`FUN_014bcbac` 与对应 ELF VA、`FUN_012034fc` 与对应 ELF VA，分别相差 `0x100000`。可能是 Ghidra image base/rebase 的正常转换，也可能是抄写问题；未拿到数据库前不能判错，也不能混用。

### 1.2 确认：当前假对象方案不能证明菜单加载语义已恢复

报告的当前方案是 cloudcell 和菜单加载器都使用静态缓冲区，vtable 分别全填 stub；并通过 `return self` 使调用后 `x0` 有值。[P：§2，当前方案]

这至多能支持一部分调用链“不立即访问空指针”。如果实际被调用的菜单槽位仍是无业务副作用的空函数，则它不会凭空建立真实资源任务、更新菜单对象或完成初始化。是否还有其他加载入口，必须靠调用跟踪确认。

**禁止继续扩充空 vtable 作为主线修复。也禁止把真实 vptr 复制到一块未经真实构造的裸缓冲区，再直接调用真实成员函数。**

### 1.3 高优先级假设：菜单地址仍混淆 GOT 槽与全局变量

报告同时给出：

```asm
ldr x0, [x23]    // 菜单加载器；注释称 x23 = *(0x1f6df50)
```

并记录创建菜单加载器时触及 RELRO 只读区域。[P：§2，修复尝试；§3，主渲染路径]

如果注释准确，其链条应首先按下面的候选解释验证：

```text
runtime(0x1F6DF50)  →  一个槽位
读槽位              →  保存全局对象指针的地址（x23）
再读这个地址         →  菜单对象指针（x0）
读菜单对象           →  vptr
读 vptr + 168       →  此次实际调用的目标
```

这是候选解释，不是已确认内存布局。应查 `x23` 的定义点、ELF 节/段、对应 relocation 类型与符号，再做运行期逐层验证。

**若这个地址实际是 GOT 槽，RELRO 报错可能首先说明写错层级，而非“还缺一种改权限技巧”。** 即使找到可写的真实变量，也应优先让正确工厂/构造路径设置它，而不是直接塞假对象。

### 1.4 确认：`vtable+272` 并不天然超出 40 个 ARM64 指针槽位

报告记录“40 条目假 vtable，vtable+272 为 NULL”，随后改为 64 条目。[P：§2，修复尝试]

在这里明确采用的“每个函数槽位 8 字节、从当前 vptr address point 起算”假设下：

```text
272 / 8 = 34
40 个槽位覆盖索引 0..39
```

所以单纯扩大到 64 个槽位并没有解释原来的 NULL。应先确认是否读到了预期对象与 vptr、是否真的填满该槽位、表的 address point 是否正确、对象是否失效或被覆盖。C++ ABI 的 vptr address point 不必等于整张 vtable 的起始地址。[S2]

### 1.5 尚未确认：cloudcell 是不是唯一、最早的阻塞点

报告把根因链写成“cloudcell 未真正初始化 → 跳过菜单加载”。这是有价值的假设，但当前输入没有真实调用日志、回调注册表、对象创建轨迹或全部分支取值，不能将其升级为已证实的唯一根因。[P：§2，根因链]

实际还需要区分：地址错误、对象类型/生命周期错误、未交付的异步完成事件、guest errno/TLS 错配、任务队列未消费，以及菜单请求之后才发生的资源/渲染问题。

## 2. 先修正对调用链的理解

报告里的关键片段是：[P：§3，主渲染路径]

```asm
ldr x8, [x0]
ldr x8, [x8, #48]
blr x8
ldr x8, [x0]
ldr x8, [x8, #136]
blr x8
tbnz w0, #0, skip
...
ldr x8, [x0]
ldr x8, [x8, #168]
blr x8
```

AAPCS64 把 `x0..x7` 用作参数/结果寄存器，并非要求被调用函数保持原有 `x0`。[S1]

因此，当前最合理的待验证语义是：

| 位置 | 从调用方能看出的最低要求 | 不能直接假定的事情 |
|---|---|---|
| 第一次 `vptr+48` | 返回后，`x0` 被当作可解引用对象使用 | 返回对象一定就是原来的 self；返回类型已完整确定 |
| 返回对象的 `vptr+136` | 返回值的 bit 0 被检查 | 所有非零值都跳过；可以统一返回指针充数 |
| 菜单对象的 `vptr+168` | 调用前显式设置 `w1=2`、`w2=0x60` | 此函数一定同步读文件；其他寄存器/隐藏参数没有意义 |

`extern "C"` 不是“保持 x0”的修复手段；`return self` 只是给 `x0` 放入一个指针。必须恢复每个槽位自己的参数、返回值和副作用契约，而不是统一返回一个对象地址。

特别注意：`tbnz w0,#0` 看的是最低位。一个对齐指针的最低位可能恰好为 0，使错误实现看起来“通过门控”；这不能证明它正确实现了布尔或状态返回。

调查这条链时，不要只看第一个对象的 vtable。第一次调用可能返回另一个对象/子对象，需要重新记录第二个对象的 vptr 和目标函数。

## 3. 执行顺序：先电脑审计，再有目的地跑真机

### P0：保全基线、统一地址；不需要 Switch

保留当前可回滚的源码状态和 NRO，不覆盖唯一产物。先检查已有版本管理/工作区状态，不能擅自清空用户未提交修改。

记录：源码 commit/dirty 状态、NRO SHA、四个 DSO 的 SHA、APK versionName/versionCode（仓库可获得时）、已有资源 manifest，以及当前启动模式。报告给出的 SHA 只能作预期值，必须与实际文件核对。

所有地址使用统一记录：

```text
module_id / module_sha256
label / address_kind
elf_va / ghidra_va / ghidra_base_conversion
runtime_load_bias
file_offset（仅在存在文件字节时）
expected_segment_permissions
pointer_indirection_chain
source_evidence
```

同一个 DSO 内：

```text
runtime_address = module_load_bias + elf_va
module_load_bias = actual_guest_anchor_runtime - anchor_elf_va
```

其中 anchor 必须是已确认的 guest 代码地址，不是 host JNI wrapper、未解引用 GOT 槽或另一模块的同名符号。四个 DSO 分别计算 load bias，不能跨模块共享一个 delta 基准。[S5]

先运行附件只读审计脚本，再核查真实 ELF。脚本只查报告算术、可选 SHA/ELF 段范围，不能代替反汇编验证。不要仅为了使审计变绿而掩盖原报告错误。

**P0 验收：** 已分类所有现有强制状态、假对象和补丁；所有将要读取/调用/写入的目标具有模块身份和二进制依据；未解决的地址禁止进入候选修复包。

### P1：三路小范围只读分析；不同时改核心代码

工具支持子代理时执行三路；否则按同样任务顺序执行。不要假设当前聊天已启动了这些代理。

| 分工 | 读取范围 | 必须回答 | 输出 |
|---|---|---|---|
| A：地址/对象 | `guest_view_probe.cpp`、`multi_dso_linker.cpp`、相应反编译和 relocation | 两个全局地址各是哪一层？真实对象由谁创建、赋值、销毁？ | `address_object_audit.md` |
| B：JNI/事件 | `jni_bridge.cpp`、APK DEX 中相关类、生命周期与回调交叉引用 | `getComponent` 的真实类型是什么？谁注册 token、谁发完成事件、在哪个线程消费？ | `jni_event_contract.md` |
| C：菜单/资源 | `guest_filesystem.cpp`、菜单候选调用链、已有文件访问日志 | 真实菜单任务的生产者/消费者是谁？第一笔资源请求应该是什么？ | `menu_request_chain.md` |

各报告只交付相关结论：证据位置、调用方/被调方、目前缺失的证据、一个最小实验。建议每份先限制在约 150 行以内，不输出整个反编译目录。

主代理统一选择“最早偏离真实契约的一处”修改。不得三路同时编辑 `guest_view_probe.cpp`，不得把 A/B/C 三套试探补丁一起合并。

**P1 验收：** 至少能明确下一轮要区分的两种情况，以及一条观测分别如何支持/反驳它们。不能只写“再试试 cloudcell”。

### P2：制作可观测诊断版；一次复制，多次独立冷启动

诊断版不以“把菜单硬叫出来”为目的，优先保持行为可解释。

建议内置以下模式，复用现有启动方式或少量 host 端选项，不要求复制额外数据卷：

| 模式 | 用途 | 规则 |
|---|---|---|
| `OBSERVE_CURRENT` | 观察当前方案作为对照 | 保持已知行为，所有 fake 对象/强制写入都显式打标；不能作为最终通过依据 |
| `REAL_INIT_PATH` | 看真实初始化最早停在哪里 | 关闭假 cloudcell、假菜单对象和强制 ready/frameState；保留已经验证正确的必要平台兼容层 |
| `CANDIDATE_FIX` | 后续验证一项有证据的修复 | 在真实路径上只增加一项因果明确的修复；不是另一组状态硬写 |

**每种模式都重新启动 NRO。** 不在同一进程里先构造假对象，再切换“真实对象模式”；不要假定 DSO 构造器、TLS、全局单例和 JNI 引用能完整重置。

“一次复制”不等于“一次冷启动就跑完全部实验”，也不是承诺一次修复成功。目的是减少传包，而不是牺牲变量隔离。

不要盲目撤销 `connect()` 快速失败带来的进展；先检查它是否正确传递 guest 侧 errno、重试/终态语义和上层回调。主线程不会卡在 connect，并不证明上层初始化已完成。

**P2 验收：** 一份日志能回答“最后完成什么、正在等待什么、谁应该使它完成”，而不只是“仍然蓝屏”。

### P3：补最小真实契约，而不是补一个新的布尔值

按日志显示的最早失败环节选择一种修复；以下只是分流规则，不是已确认病因。

| 观测 | 下一步 | 不应做的事 |
|---|---|---|
| 真对象从未由工厂创建 | 核查 Android/JNI 创建入口、组件类型、依赖的最小初始化 | 再分配一个全零对象 |
| 对象存在，等待已注册的初始化事件 | 恢复相应合法离线/失败分支和事件投递，保留原线程/顺序要求 | 无注册记录地发送 id=0；伪造远程成功 |
| `+48` 返回无效对象 | 还原真实返回契约/对象生命周期 | 统一返回 self |
| 菜单全局解析错误 | 根据 relocation 和 x23 定义修正地址层级 | 给整页 RELRO 开写权限掩盖错误 |
| 菜单任务入队，但没有被消费 | 查消费者线程、唤醒/等待、时钟、线程初始化与 JNI/TLS | 重复无限触发菜单请求 |
| 已消费菜单请求，但打开资源失败 | 查精确路径、大小写、卷选择、存在性、返回码 | 重打全部数据卷或先做纹理优化 |
| 文件读取完成，解析失败 | 比较长度/偏移/格式及实际解码流程 | 仅凭 magic 判定“必须解密” |
| 资源与纹理已上传，画面仍异常 | 此时转入 guest GL 状态、格式、shader/FBO/纹理完整性检查 | 继续把所有问题归到 cloudcell |

静态构造缓冲区 + 假 vtable 只能留在独立探针测试中帮助验证观察器，不进入正式恢复路径。

### P4：确认菜单闭环，再推进比赛

最小通过证据应相互独立：

```text
真实对象/合法服务替代对象的身份与生命周期有据可查
    +
初始化事件有注册、产生、消费和最终结果
    +
真实菜单状态请求被任务消费者执行
    +
实际菜单资源成功读取并被解析/使用
    +
菜单首帧可见，输入可使菜单状态变化
```

建议用重复冷启动检查偶然成功，但不预先承诺固定真机轮数。至少记录所用模式、build ID、是否复用本地存档、每次到达的最远里程碑。

## 4. 只加入能回答问题的观测

### 4.1 地址/对象观测

逐层记录 GOT 槽地址、槽值、全局存储地址、对象地址、vptr 和本次实际调用目标。每次解引用前验证范围/映射与访问权限，不能让诊断代码自身用未知指针崩溃。

标记地址归属：guest 哪个 DSO 的哪个段、guest 分配器对象、host 兼容对象或未知区域。执行目标既可能是 guest 代码也可能是经确认的 host shim，不能机械要求所有函数地址必须在一个 DSO 内。

必须记录 `+48` 调用前的对象，以及调用后 `x0` 返回的对象；随后记录第二个对象 `+136` 的返回 bit 0。未经验证的调用约定不能靠任意函数指针强转来“探测”。

无法安全 hook 时，优先利用现有 loader/JNI/VFS/shim 边界；不要为加日志先发明新一套运行期代码补丁框架。

### 4.2 JNI/异步观测

对本路径实际涉及的方法记录：

```text
class_name + method_name + JNI_descriptor
static_or_instance
return_kind
receiver_handle / object_type / generation
thread_id / lifecycle_epoch
request_id_or_timer_token
register → schedule → dispatch → complete/fail/cancel
```

日志例子必须带 `EXAMPLE` 标记，不能混入真机输出充当证据。业务账号、授权 token、请求正文等敏感数据不进入诊断日志。

JNI 的 `JNIEnv` 有线程关联，不能因 onCreate/onResume 正常返回就假定工作线程、引用寿命、异步回调也全部正确。[S3][S4]

建立明确的对象/句柄注册表，而不是所有 `getComponent` 都返回同一个 dummy。具体类型、方法签名、返回对象与线程模型以实际 APK/反编译为准。

记录请求注册与消费的对应关系。**0 不是在所有系统中都非法的 ID**；问题是不能凭空构造未注册、过期或错误类型的 ID。报告中的 id=0 崩溃只能说明那些尝试没有得到有效上下文。[P：§2，修复尝试]

若原调用约定要求异步返回后再完成，就必须先注册并排队，再在正确时机投递，不能在注册函数尚未返回时同步重入 native 回调。

### 4.3 资源观测

每次关键请求记录“guest 原路径 → 规范化路径 → 选定 ROMFS/可写保存目录 → 打开结果 → 返回字节数 → 解析结果”。

七个只读资源卷与可写存档/配置路径分开检查。卷存在、`.so` SHA 匹配，均不能替代存档可用性、资源版本一致性和实际读取成功的验证。

优先记录真实请求路径；`MainMenu.gui`、`sprites_*` 是报告中的观察指标，而不是所有版本都必须满足的硬编码唯一文件名。[P：§2、§4]

### 4.4 防止日志反过来制造问题

使用有界缓冲、首次出现与状态变化日志，加累计计数；不要每帧把所有 JNI/GL 调用同步写入 SD 卡。建议缓冲上限先控制在约 1 MiB，实际大小由项目实现决定。

必须记录丢弃事件数，日志不完整时不能由“没看到事件”推出“事件没发生”。在里程碑、受控停止点和错误处保存摘要。

看门狗报告“规定观测窗口内没有状态进展”即可；计数达到 30 秒不自动证明死锁。窗口应与 Android 参考路径和实际任务状态比较，不使用固定帧数代替时钟与因果证据。

对 C：先查写入目标是否真是 GOT/RELRO、是否写错层级。需要 loader 修正时，在允许的装载/重定位阶段完成受控操作，然后按段恢复权限；不要采用“所有 `.text` 常驻 RWX”。Android linker 明确在 relocation 后保护 GNU RELRO。[S5]

libnx 的 JIT 实现有可写/可执行地址及权限转换路径，还会检查环境提供的 syscall 能力；它不是任意现有内存块 `svcSetMemoryPermission` 都能改成功的保证。[S6][S7] 只能在现有 loader 拥有且环境支持的映射路径上做改动。能力不满足就标记阻塞，不靠放宽全局权限继续碰运气。

对 D：`magic 31423a44` 本身不足以确定是加密、压缩还是序列化容器。报告记录该文件已被读取，因此不应在没有内容与调用证据时把“先解密 GUI”升级成必经任务。[P：§6]

## 7. 里程碑与失败分流

这是验收依赖图，不要求游戏内部回调严格按本表顺序发生；实际偏序以原程序证据为准。

| 关卡 | 通过证据 | 未通过时只检查 |
|---|---|---|
| S0：身份与地址可信 | 原文件身份匹配，模块/VA/运行地址/目标指令或数据性质核验 | 地址与 loader |
| S1：真实对象可用 | 创建者、存储位置、vptr、生命周期记录完整 | 工厂、JNI 类型、依赖初始化 |
| S2：前置事件闭环 | 有注册、有投递、有消费，得到真实本地结果或合法失败终态 | 异步契约、线程/TLS/时钟/错误语义 |
| S3：菜单请求被执行 | 真调用目标与任务生产/消费链可追踪 | 菜单门控与队列 |
| S4：菜单资产可用 | 实际请求成功读取、长度合理、解析或消费成功 | VFS、格式、版本与本地数据 |
| S5：真实菜单可交互 | guest 菜单画面可见，输入使菜单状态改变 | guest 图形/输入接口 |
| S6：离线比赛闭环 | 进入比赛、驾驶、完成、返回菜单、安全退出 | 仿真/存档/生命周期 |

只有 S4 已具备而 S5 失败时，才把主要排查资源转向 GL 渲染。host 四边形正常是已有成果，但不能证明 guest 的所有纹理、shader 和状态组合都兼容。[P：§2]
