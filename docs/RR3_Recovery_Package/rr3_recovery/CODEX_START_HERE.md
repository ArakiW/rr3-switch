# Codex 首轮任务：先纠偏，后发包

你在本地 RR3 Android ARM64 → Switch libnx NRO 仓库中工作。先读仓库当前 `PROJECT_STATUS.md` 与附件 `RR3_RECOVERY_PLAN.md`。报告可能落后于代码：发生冲突时保留冲突记录，以当前文件、原始二进制和真实日志验证，不机械回滚已被证实的进展。

## 任务目标

目前 hideSplash 后没有菜单资源加载。首轮不要以“再做一版能进菜单的补丁”为目标；先确认地址与对象身份，定位真实初始化路径的第一个缺失环节，给出一项能区分原因的最小实验或一项已有证据的最小修复。

保留四 DSO 加载器、已有生命周期和图形探针成果。七个 ROMFS 数据卷不变。不绕过 DRM，不伪造账号/授权，不伪造远程成功，不分发 EA 数据。

## 工作纪律

先读取实际源文件、反编译和日志。文档上的“根因”只是待验证假设。不要把函数能返回、帧数增加或 host 四边形成功当作 guest 菜单已恢复。

不扩大 fake vtable，不全体 return self，不强制 ready/frameState 作为修复，不无注册记录地注入 HTTP/Timer 回调，不写未知地址，不把所有 text 改成 RWX，不重复调用真实构造器，不重打资源卷，不做无关大重构。

保全当前源码与可回滚 NRO；不得清空用户未提交修改。只读审计不阻塞在不必要的确认问题上；遇到缺少二进制/日志等实际证据，明确标记缺口，完成仍可完成的静态部分，不能造证据。

## 第一批必须回答的五个问题

### A. 错误 delta 是否进入代码？

报告中：

```text
anchor onViewRenderJNI ELF VA = 0x12B3614
hideSplash ELF VA            = 0x12AEEE0
正确表内 delta               = -0x4734
报告 delta                   = -0x4E1634
错误 delta 实际对应 ELF VA     = 0xDD1FE0
```

搜索 delta、绝对值、表达式和地址清单。确认是报告错误还是实际代码错误。根据原始 DSO 验证目标指令，不凭表直接改代码。核对 FUN_ 标签与 ELF VA 相差 0x100000 的两个记录是否属于 Ghidra rebase。

### B. 菜单全局到底是几层指针？

从报告中的 `ldr x0,[x23]` 反向追踪 x23。对 `0x1F6DF50` 检查节/段、relocation、GOT 槽、全局存储、对象、vptr 的完整链条。记录每层的模块与权限。

查清原 RELRO 失败是不是把 GOT 槽当成了可写对象变量。不要先尝试新的改权限办法。

### C. 三次虚调用各是什么契约？

分别核查原对象 `vptr+48`、返回对象 `vptr+136`、菜单对象 `vptr+168`。

第一次调用后的 x0 被解引用，因此需要有效返回对象，不等于必须保留原 self。`tbnz w0,#0` 只测试 bit 0；不能统一返回指针。168 调用前 w1=2、w2=0x60，其真实业务与其他参数以原代码验证。

报告的 vtable+272 在 8 字节槽位下是索引34，在40条目内；先解释当时实际 vptr/填充/生命周期，不再扩容猜测。

### D. `getComponent` 和初始化事件是否真实闭环？

对照 APK 的类、完整 JNI descriptor 和 native 调用点，找出真实组件类型、创建路径、回调注册 token、投递线程和消费者。只还原离线启动涉及的最小契约。

审计 connect 快速失败是否正确传递 guest errno 和终态；网络“不再阻塞”与上层初始化“已经完成”是两回事。不伪造成功响应。

### E. 第一笔真实菜单任务/资产请求在哪里？

追踪真实菜单请求的产生、队列、消费者和文件读取。文件名以此版本实际路径为准，不把 MainMenu.gui 设为唯一通过标准。

菜单调用只返回而没有副作用不算通过；任务入队但没有消费者时，应查任务调度而不是无限重发。

## 执行方式

有子代理工具时，最多开三路只读分析：地址/对象、JNI/事件、菜单/资源。每路先交相关证据与一项实验，主代理统一选择并实施一个变更。工具不支持就顺序完成，不能宣称已运行并行代理。

主代理先交付：

```text
1. 已验证事实 / 文档冲突 / 待验证假设
2. 地址与对象链条，附源文件或反汇编位置
3. JNI/异步事件的最小契约
4. 当前最早缺失的里程碑，或还缺哪项观测才能确定
5. 下一轮唯一主要假设及其反证条件
6. 最小修改集合与回滚方法
```

若静态证据不足，设计同一 NRO 的对照/真实路径诊断模式，每次模式分别冷启动；不要在一次进程生命周期内重复初始化 guest。记录真实对象、请求注册/消费、精确文件路径及结果。避免逐帧全量日志，记录丢弃事件数。

## 电脑检查

可在任意目录运行附件的只读审计器，参数替换成实际路径：

```powershell
python audit_rr3_status.py "E:\AI\RealRacing3-switch\PROJECT_STATUS.md" --out status_audit.json
```

原始 DSO 可用时增加：

```powershell
python audit_rr3_status.py "E:\AI\RealRacing3-switch\PROJECT_STATUS.md" --elf "E:\AI\RealRacing3-switch\reverse\native\arm64\libRealRacing3.so" --out status_elf_audit.json
```

上传的原报告会因 delta 算术错误返回退出码1，这是审计发现，不是脚本异常。退出码2才是输入/工具错误。报告算术通过不代表二进制地址、对象或运行行为通过。

先识别项目测试框架，然后使用真实测试执行器。确认收集与执行数量；不要默认 `python test_*.py` 已运行全部测试。附件脚本自己的单元测试不是项目的11个契约测试。

## 发包条件

确认要观测/修改的目标地址、调用约定与模块身份；电脑测试已执行并有结果；改动只有一个主要因果假设。否则只交审计结果，不发另一个盲猜 NRO。

发包继续复用现有 Build-NativeSwitch.ps1，更新 NRO manifest/checksum，保留基线，不动七个资源卷。写清模式选择与现有 ZR→ZL→ZL 操作是否有变化。

## 首个通过目标

真实初始化或合法离线失败分支闭环 → 真实菜单请求被消费 → 第一笔实际菜单资源读取并使用。

下一阶段才验收菜单首帧与输入，再验收单场比赛。没有真实日志的进展一律标记“未验证”，不要给成功率百分比或承诺固定几轮必定成功。
