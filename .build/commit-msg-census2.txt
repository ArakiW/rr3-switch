THE CENSUS READS COUNTERS NOW, THE TRACE IS THIN, AND THE AA HYPOTHESIS IS REFUSED

MEASURED 2026-11-10, rounds census2 (AA_LEVEL = 4) and aa0 (AA_LEVEL = 0), the

THE CENSUS READS THE PORT'S COUNTERS NOW.  The port counts the resolution
EVENTS for the main menu's layout and for the two-square panel, and the census
line carries them (gui=, twosq=): census2's census line reads "gui=75 twosq=15",
which is EXACTLY what the log-text grep reported in yield2 (15 and 75) -- so
the counter measures the same thing, and the measurement no longer depends on
what the port writes.  The census script reads the counters and falls back to
the text only for an older log.

AND THE TRACE CAN BE THINNED FOR REAL.  With the census off the log's text, the
path trace is written only for the gui/processed/ subtree and the rest is

    yield2   124,464 log lines   52.9 per frame

AND THE ANTI-ALIASING HYPOTHESIS IS REFUSED BY THE MEASUREMENT.  The card was
running AA_LEVEL = 4 (four samples per pixel), which looked like the obvious
lever on the guest's rasterisation.  Turning it off did NOT make the frame
faster:

    round        AA_LEVEL   tt median   jni median   jnioth mean   fs mean
    census2          4        72.0 ms      8.0 ms      164.2 ms    43.8 ms
    aa0              0        83.0 ms      0.0 ms      221.3 ms    10.3 ms

So the frame's remaining cost is the GUEST'S OWN WORK -- the Java and C++ method
bodies that run inside the JNI dispatch (jnioth), which the port cannot change
-- and the emulator's GL path on top of it.  The port's own share is now about
a millisecond a frame (tp 0.4 ms, fs 0 ms).
