# The port reads this file at sdmc:/switch/rr3-native-rehost/rr3-screen.txt.
# An ABSENT file means "answer the constants this port has always answered",
# so a run without this file is byte-for-byte the run that was measured
# before.  Keys:
#
#   platform=WxH   Platform.getScreenWidth / getScreenHeight
#   ui=WxH         CCUserInterfaceManager.getScreenWidth / getScreenHeight
#   view=WxH       the size the port tells the GUEST its view is
#
# ---------------------------------------------------------------------------
# WHY THERE IS A "view" KEY
#
# This is the one that decides the picture quality.  MEASURED 2026-10-28,
# the guest's own log:
#
#   Res base: 1280x720
#   Res order:
#   (960.000000, 640.000000) - 1.500000 - gui_assets/960x640/
#   (480.000000, 320.000000) - 1.500000 - gui_assets/480x320/
#
# The 2D UI is drawn from a 960x640 atlas into a 1280x720 frame: a 1.33x
# upscale of every sprite and glyph.  That is what "the picture is soft" is.
# The HD volume ships a complete gui_assets/2048x1536 tree and the guest
# never picks it.
#
# THE REASON IS THE GUEST'S OWN FILTER, and it is not the filesystem.  In the
# guest's cc::ImageResManager (ELF 0x10f8cf8) every folder in the gui_assets
# listing is parsed with sscanf("%ux%u") and then kept only if
#
#     width <= screenW  OR  height <= screenH
#
# (ELF 0x10f8ec8-0x10f8edc).  2048x1536 fails both tests against a 1280x720
# screen, so it is dropped BEFORE the sort and is never a candidate.  The
# port already puts 2048x1536 into the listing (measured: the guest lists
# it), and the guest still drops it -- so there is nothing to fix on the
# filesystem side.
#
# The screen size is the ONLY lever, and it is the size the port hands the
# guest in onViewChangedJNI.  The present path already renders the guest
# into its own framebuffer and blits it out, so a bigger view is a bigger
# render target and a scaled blit -- which also gives the 3D scene 2x
# supersampling for free.
#
# THE COST, STATED PLAINLY: the UI layout moves with the view size, so the
# touch script's pixel coordinates have to be re-measured; and the 3D scene
# gets more pixels to fill.
#
# ---------------------------------------------------------------------------
# THE EXPERIMENTS (2026-10-28)
#
# platform=2048x1152 -- MEASURED, NO EFFECT.  The port's own line proves the
# override reached the guest ("screen-override ... platform=2048x1152") and
# the guest's answer did not move ("Res base: 1280x720").  The Platform
# screen is NOT where the guest's screen comes from.  The evidence is kept
# here; the ACTIVE value below is no longer that experiment.
#
# view=2048x1536 -- the 4:3 view.  The 2D UI becomes exactly 1:1 (the HD
# atlas IS 2048x1536), which is the sharpest possible; the 3D scene is
# rendered 4:3 and the blit has to letterbox or crop it.  Superseded: the
# present path keeps the aspect ratio and puts black bars on the sides, and
# the 3D scene loses 160 pixels of width for nothing.
#
# view=2048x1152 -- the 16:9 view.  MEASURED, GOOD (archive
# 20261028-211808-eden-q7):
#
#   Res base: 2048x1152
#   Res order:
#   (2048.000000, 1536.000000) - gui_assets/2048x1536/     <-- FIRST
#   (960.000000, 640.000000)   - gui_assets/960x640/
#   (480.000000, 320.000320)   - gui_assets/480x320/
#   share) Current res: 2048, 1152
#   view=2048x1152  present=0,0 1280x720
#
# Three independent instruments agree that the picture is fixed: the atlas
# load failures went 125 -> 0, the LocalStyles failures disappeared, and the
# 240 asset digests matched with src=rr3gui0: (the real HD volume).  The
# present rect is the whole 1280x720 screen with no black bars, because
# 2048/1152 and 1280/720 are both 16:9.
#
# WHY 16:9 STILL PICKS THE 4:3 ATLAS.  The guest's own comparator
# (ELF 0x10f9948) compares the node's HEIGHT first and its WIDTH second --
# not the aspect ratio -- and the third gate, ALLOW_RETINA, is true at run
# time.  So the winner is the tallest tree that passes the filter, and
# 2048x1536 passes it because the VIEW is 2048x1152 (1536 > 1152 is not
# required; the filter is an OR).
#
# TO GO BACK TO THE OLD PICTURE: change the three lines below to 1280x720
# and redeploy.  That is the layout the touch script's pixel coordinates were
# measured on.
#
# ---------------------------------------------------------------------------
# THE ACTIVE CONFIGURATION: 2048x1152 -- THE PICTURE THE PORT IS FOR
#
# WHY IT IS HERE NOW.  The HD tree and the HD quality are PROVEN (q7 above).
# The lap counter was measured on the OLD layout, because the touch script's
# pixel coordinates were measured there and at 2048x1152 the guest lays the
# front end out differently (q7 sat on the full-screen event card and never
# reached a race: msStartLights 0).  So the value store was measured on the
# 1280x720 layout, as a clean A/B against q4 -- same layout, same script,
# the only difference being the value-store fix.
#
# THAT MEASUREMENT IS DONE, AND IT PASSED (archive 20261028-213445-eden-q8):
# 717 of 717 "race-metrics-scan" lines reported ok=1 with lapsWhy=none, which
# is the GUEST'S OWN integrity check agreeing with the port's four cells.
# Before the fix, every single lookup failed.  The lap counter itself still
# reads -1, and that is NOT a reading failure: the guest's own "Total Laps"
# member says -1 as well, because the car never completed a lap -- it drove
# 125,841 spline units and stopped against something, and the port's
# autopilot reversed itself 24 times without getting free.
#
# SO THE LAYOUT IS NO LONGER THE BLOCKER, and the card goes back to the HD
# configuration, which is the picture the port is for.
#
# WHAT IS STILL LAYOUT-DEPENDENT: the touch script (rr3-touch.txt) is a list
# of PIXEL coordinates measured on the 1280x720 layout.  At 2048x1152 the
# guest draws the same screens at a different scale, so the same pixels land
# on different widgets.  The script has to be re-measured against the HD
# frames before an automated round can drive into a race again -- the
# guest's own red glove cursor shows where it wants to be pressed (measured
# in the q7 frames at about (762, 138)).
#
platform=2048x1152
ui=2048x1152
view=2048x1152
