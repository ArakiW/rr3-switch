# The path to a race, hop by hop.
#
# MEASURED 2026-10-25 (archive 20261025-161933-eden-f1a): every coordinate
# below was read off a framebuffer capture or off the guest's own on-screen
# text rectangle, and every hop was confirmed by the screen that followed it.
#
#  1. EVERY LOGIN opens the M$ DAILY REWARDS calendar.  Its orange
#     "\u6536\u96c6" (COLLECT) word is at x 198..404, y 191..255.  Clicking
#     it opens the popup in step 2.  (The rectangle comes from the guest's
#     own text-quad record: screenX=198, screenY=191, w=206, h=64.)
#     -- SEE THE FIX AT THE END OF THIS FILE: this coordinate MOVES with
#     the date, so it is no longer used on its own.
#  2. the "\u60a8\u7684\u6bcf\u65e5\u5956\u52b1" (YOUR DAILY REWARD) popup's
#     orange COLLECT bar is x 396..884, y 525..573, and its label is at
#     x 611..683, y 536..566.  The centre of the label is (647, 551); the
#     point used here is (640, 549), which is inside the label.
#  3. behind both of those is the main menu.  Its right-hand column is the
#     daily race and its orange "\u8fdb\u5165\u6bd4\u8d5b" (ENTER THE RACE)
#     label is at x 1113..1235, y 613..639.  Its centre is (1174, 626).
#  4. the event picker ("\u9009\u62e9\u8d5b\u4e8b", CHOOSE EVENT) offers three
#     daily-race cards; the first is "\u8d8a\u91ce\u8d5b" (OFF-ROAD), whose
#     title is at x 250..420, y 415..480.  Its centre is (335, 450).
#  5. the F1 Academy quest page ("\u901a\u5f80FORMULA 1\u00ae\u4e4b\u8def")
#     ends in a "\u7ee7\u7eed" (CONTINUE) label at x 883..943, y 488..512.
#     Its centre is (913, 500).  The guest lends the player a car here
#     ("\u4f60\u501f\u5230\u4e86\u4e00\u8f86\u8f66\u3002").
#  6. the car select screen's "\u5f00\u59cb\u6bd4\u8d5b" (START THE RACE) is
#     the control at the bottom right, (1114, 698) -- the coordinate the
#     20261024-102025-eden-race-door archive used, and the one that made the
#     guest try to load a track in f1a.
#
# The hops are spaced so that each transition has time to settle, and so
# that a framebuffer capture lands on both sides of each of them.
#
# Nothing else is clicked: a click in the left half of the screen is a
# STEER in the race, and steering taps throw the car off the track.
#
# ---------------------------------------------------------------------------
# FIXED 2026-10-27, after archive 20261027-172023-eden-f1k.
#
# HOP 1's X WAS WRONG, AND THE TOUCH LANDED 72 PIXELS TOO FAR LEFT.
#
# The framebuffer captures of that run were measured pixel by pixel (the
# orange button mask: r>230, 150<g<215, b<60), and they say the calendar's
# orange COLLECT button is at
#     x 373..533, y 202..242      -> centre (453, 222)
# and not at x 198..404.  Hop 1 clicked (301, 223): on the button's left
# edge, in the margin.  The consequence was measured, not guessed:
#
#   frame   300 .. 4100   the CALENDAR, still up (the click missed)
#   frame  4200 ..        the POPUP, opened by hop 4's (335, 450) -- a click
#                         meant for the event picker, which landed on a
#                         calendar day instead
#   frame 12000           the POPUP, still up, with hop 2's click on its
#                         COLLECT bar long gone (it fired at frame 1900,
#                         before the popup existed)
#
# So the guest spent the whole run inside a modal it could not dismiss, and
# never reached the main menu.  Every other coordinate in this file is
# confirmed by the f1a archive, and hop 2's target was confirmed again in
# f1k: the popup's COLLECT label sits under the guest's own red glove
# sprite at (640, 549).
#
# The frame numbers are left exactly as measured on f1a: with hop 1
# actually landing, the calendar closes at ~1400, the popup is up for
# hop 2 at 1900, and the rest of the path follows the same spacing.
#
# ---------------------------------------------------------------------------
# ADDED 2026-10-27, after archive 20261027-170602-eden-f1k.
#
# HOP 7: THE "CONTINUE" THE GAME ASKS FOR AFTER THE TRACK LOADS.
#
# MEASURED on that run: the guest walked the whole path -- calendar, reward
# popup, main menu, event picker, F1 Academy quest, car select -- and the
# track load finished ("Total Levelloading: 18554", Silverstone).  Then the
# game put a modal up in the middle of the screen: a cream panel with a
# progress bar and a yellow "继续" (CONTINUE) button, with the guest's own
# red glove sprite sitting ON that button.  The guest draws that glove on
# the control it wants pressed, so the button is the thing to click.
#
# Measured off the framebuffer, the same way hop 1 was measured (yellow
# mask r>225, g>215, b<90): the button is at x 687..1023, y 455..514, so
# its centre is (855, 484).
#
# WHY FOUR FRAMES AND NOT ONE: the track load finishes when the assets
# finish arriving, and that is not a fixed frame.  In that run the panel
# was up at frame 8,400 (t=807 s) after the load began around frame 4,000.
# A single guess would be a single point of failure, so the click is
# repeated across the window the panel can plausibly appear in.  The button
# is in the RIGHT half of the screen (x=855 > 640), which is NOT the
# touch-steering half -- a click that lands after the race has started is
# therefore harmless.
# ---------------------------------------------------------------------------
# FIXED 2026-10-29, after archives 20261029-000257-eden-q12 onwards.
#
# HOP 1's COORDINATE MOVES WITH THE DATE, AND A HARD-CODED ONE CANNOT
# SURVIVE IT.  THIS IS WHY THE GUEST STOPPED REACHING A RACE.
#
# MEASURED.  q11 (2026-10-28 22:59) reached a race; q12 (2026-10-29 00:02)
# and every run after it did not.  The two runs are identical up to guest
# ordinal 2500: the same touch injections at the same frames, the same view
# size (1280x720), the same touch channel state (valid=1, enabled=1), the
# same asset lists, the same sync traffic.  The difference is ONE MODAL.
#
# q12's last frame (frame-012000.png) shows the guest sitting in the M$
# DAILY REWARDS CALENDAR, with its own red glove on the orange COLLECT
# word.  q11's frame at the same point (frame-001400.png) shows the MAIN
# MENU -- no calendar at all.
#
# So on 2026-10-28 the daily reward had already been collected and the
# calendar did not open; after midnight it opened again and the guest never
# got past it.  It sat in that modal for the whole run, and every later hop
# landed on the calendar instead of the menu.
#
# THE COORDINATE IS NOT THE SAME FROM ONE DAY TO THE NEXT.  Measured off
# the real frame with the orange-button mask (r>230, 150<g<215, b<60),
# the same way the 2026-10-27 fix measured it:
#
#     2026-10-27 (archive f1k)   the COLLECT word at x 373..533, y 202..242
#                                 -> the point (453, 222) was used
#     2026-10-29 (archive q12)   the COLLECT word at x 565..725, y 202..242
#                                 -> (453, 222) is NOT orange; it is blank
#                                    background, 112 pixels left of the
#                                    button's left edge
#
# The vertical position did not move (both at y 202..242) but the horizontal
# one did, because the calendar lays its COLLECT word out over the middle
# column of a day-grid whose width depends on the month.  A single
# hard-coded point is therefore a coin toss.
#
# THE FIX: hop 1 clicks SEVERAL candidate points, spread over the width the
# word can occupy, and the guest takes the one that is actually the button.
# The extra clicks are harmless -- they land on the calendar's own day
# circles, which is a no-op (the run that got stuck proves the day circles
# are not the way out).
#
# The word's centre is at x = 453 on 2026-10-27 and x = 645 on 2026-10-29;
# the two are 192 pixels apart.  The candidates below cover x = 453, 549 and
# 645, so whichever layout the game picks, one of the three hits the word.
#
# HOP 1 is also repeated over a window rather than fired once, because the
# calendar opens at a time of its own choosing: it is up when the guest
# logs in, and the guest may need a moment to lay it out.  Each repeat is
# harmless while the calendar is up (a click on the button collects it, and
# after that the calendar is gone and the click lands on the main menu,
# which is where hop 2 and later expect to be).
#
# The same drift can hit the other hops, so each of them is repeated over a
# short window as well: a hop that lands on the wrong control is retried,
# and the guest moves on when the screen changes.
# ---------------------------------------------------------------------------
