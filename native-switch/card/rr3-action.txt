#
#   Soaks|QUEUE SOAK:RACE LOOP   fn 0xa6e22c  push_back(3)
#   Soaks|START SOAK             fn 0xa6e1e8  SoakMgr::Start(0)
#   Soaks|CLEAR SOAKS            fn 0xa6e218  clears the queue
#
# MEASURED 2026-10-30 (archive 20261030-231541-eden-rr3-q27-race-gate-action):
# all four commands were called with arg=0x0 and no owner -- which is what
# the instruction-level analysis said, because the two QUEUE commands
# overwrite x0 before they use it -- and the guest wrote its OWN automation
# log to the card:
#
#   AUTOMATION LOG [Debug]:  Start Test SOAK TEST
#   AUTOMATION LOG [Debug]:  Enter Scene 3
#   AUTOMATION LOG [Debug]:  Scene changed from None to FrontEnd, memory usage: 0 KiB
#
# -- and then the guest CRASHED: the emulator logged an Unmapped
# WriteExclusive64 at 0x8 and the guest log stopped growing for 133 s.
#
# "memory usage: 0 KiB" is the reason.  The soak framework needs a
# CONFIGURATION string per test id (0..5) out of a runtime table, and in
# this build that table is EMPTY: the race request has no data, and the
# guest dereferences a null pointer.
#
# So the Soaks route is NOT enabled here.  With an empty configuration it
# takes the guest down, and a crashed guest measures nothing.  It becomes
# the shortest route into a race the moment that table is populated.
#
# WHAT IS HERE: the unlock, which is harmless, which the guest's own
# automation did run without complaint, and which the daily race wants.
